# Проверка по одному критерию

Статус: **экспериментальный режим**, включается флагом `check --per-criterion`.
Это изменение организации запросов, а не подтверждённое исправление точности модели.
Без флага основной конвейер продолжает проверять все критерии одним запросом.

## Основание для эксперимента

В локальной диагностике пользователя Qwen прочитал значимые надписи на отдельной
картинке как в свободном, так и в структурированном ответе. При этом в общей
проверке отчёта ранее заявил об отсутствии этой картинки. В описаниях расположения
элементов остались ошибки и противоречия. Таким образом, чтение текста в этом
отдельном тесте работает, но надёжное понимание изображения не доказано.
Причина расхождения между общей проверкой и отдельной диагностикой не установлена:
в диагностике одновременно отличались количество изображений, задача и контекст.

Следующий контролируемый шаг уменьшает только число критериев в одной проверке.
Ни диагностические описания, ни предыдущий результат, ни предполагаемый правильный
балл в новые запросы не подставляются.

## Реализация

`grading/per_criterion.py` последовательно вызывает прежний `StudentWorkChecker`
или `TemplateWorkChecker`, передавая по одному критерию из копии утверждённого набора.
Названия, описания, максимумы, допустимые баллы и версия сохраняются без изменений.
Проверка записи утверждения выполняется CLI по ПОЛНОМУ набору до разделения.
В результате остаются хеш и запись утверждения именно полного исходного набора.

Каждый запрос содержит ВСЕ доказательства, разрешённые исходным конвейером:
в режиме бланка это все кандидаты после сравнения с бланком и метаданные.
Все изображения-кандидаты идут оригинальными байтами в прежнем порядке, с прежними
ID. Нет выбора «подходящей» картинки по имени, подписи, номеру или прошлому баллу.
**Это не режим «одно изображение на запрос»: количество изображений не меняется.**
Текстовые альтернативы из критериев также сохраняются.

Промпт и JSON Schema прежние; меняется только набор критериев в промпте.
Внутренний валидатор требует один результат для единственного текущего критерия.
Следующий запрос не получает историю ответов предыдущего критерия.
Результаты собираются в исходном порядке и дополнительно проверяются против
полного набора критериев. Это не суммирование/усреднение нескольких оценок одного
пункта и не выбор максимальной оценки среди попыток.

Валидация критериев, запрет ссылок на исключённые инструкции, правила статусов,
ручной проверки и сохранения результатов остаются прежними. Валидная неопределённость
с `null` не вызывает повторной попытки «до получения балла». Одна попытка исправить
невалидный ответ разрешена прежним checker-ом, не более. HTTP-ошибка не повторяется.
При неисправленной ошибке запуск останавливается: частичный результат не выдаётся
за полную проверку и не дополняется вымышленными оценками. Новый JSON тогда не
создаётся. Сохранение промежуточных результатов после каждого пункта пока не реализовано.

На восемь критериев нужно восемь последовательных запросов, максимум шестнадцать
при исправлении невалидных ответов. Используются прежняя модель, контекст и таймаут
на запрос. Режим может работать дольше общей проверки. В журнале виден прогресс
`Проверка критерия 1/8`, без текста студенческой работы.

В успешном JSON поле `inference_options.criterion_mode` равно `per_criterion`
(или `all_at_once` без флага). Баллы остаются предварительными, `grade=null`,
`teacher_confirmed=false`; предыдущий файл не перезаписывается.

## Запуск

В активном окружении проекта после обновления:

```powershell
git pull --ff-only
python -m pytest -m "not integration" -q

$work = "$HOME\Documents\StudentAIChecker\PR1"
$result = Join-Path $work ("result-per-criterion-" + (Get-Date -Format "yyyyMMdd-HHmmss") + ".json")
student-ai-checker check --per-criterion --document "$work\student.docx" --template "$work\ПР1.docx" --criteria "examples\pr1.criteria.approved.json" --approval "examples\pr1.approval.json" --output "$result"
```

Замените `student.docx` на имя локальной работы. Исходники и результаты студентов
не должны попадать в репозиторий. Сравните новый JSON со старым: не только сумму,
но все объяснения, ссылки на изображения и причины ручной проверки.
Получение большего балла само по себе не является критерием успешности изменения.

## Проверки изменения

В среде разработки выполнен `tests/test_per_criterion.py`: **25 passed**.
Тесты используют настоящий код HTTP-клиента, DOCX extractor, сравнение бланка,
валидацию и CLI; только ответы HTTP-сервера заменены `httpx.MockTransport`.
Проверены отдельные запросы, сохранность текстов/таблиц/байтов обоих PNG/ID/схемы,
изоляция истории, неизменность критериев и источников, ошибки/отмена, ограниченные
повторы, `null`, запрет засчитывать бланк, хеши утверждения и отсутствие перезаписи.
Проверены `check --help` и компиляция нового модуля, CLI и теста.
Полный существующий набор тестов здесь повторно не запускался.

Отдельно без обращения к LLM выполнена сверка предоставленных DOCX и диагностики:
хеши источника и двух изображений совпадают. Число символов system+user промпта
уменьшается с 15178 для восьми критериев до 7180–7683 для одного; в каждом остаются
два изображения, всего 376684 байта. Это измерение символов, НЕ токенов или скорости.
Ни исходники, ни ответы студента, ни диагностические описания в этот коммит не входят.

**Настоящий Ollama с новым режимом здесь не запускался.** Его влияние на качество
ещё нужно проверить локально. Это не автоматическое разбиение большого документа
и не решение всех ошибок vision. Проверка ID не доказывает истинность описания
изображения. Для достоверной оценки качества нужен набор работ, сравнение режимов
и ручные решения преподавателя, а не один удачный ответ.

Официальная справка API: https://docs.ollama.com/capabilities/vision и
https://docs.ollama.com/capabilities/structured-outputs . Поддержка изображений
и JSON Schema в API не является гарантией смысловой правильности вывода модели.
