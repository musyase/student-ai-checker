# Проверка качества оценивания

Технически исправный конвейер ещё не доказывает, что локальная модель правильно
понимает ответы студентов. Следующий этап проекта — сравнить автоматический
результат с независимой оценкой преподавателя на обезличенном наборе работ.

## Что нужно подготовить

Рекомендуемый первый набор — 10–20 работ по одной утверждённой практической
работе, включая хорошие, частичные, неправильные, пустые и неоднозначные ответы.

Для каждой работы нужны:

- обезличенный DOCX студента;
- тот же чистый шаблон DOCX;
- утверждённый файл критериев и approval-файл;
- эталонная оценка преподавателя по каждому критерию;
- пометка, должен ли случай уйти на `manual_review`.

Имена студентов, группы, даты рождения, телефоны и другие персональные данные
нужно удалить или заменить до передачи файлов. Реальные работы и журналы с
текстом ответов не добавляются в Git и не отправляются во внешние сервисы.

## Формат эталонной оценки

Для каждой работы достаточно отдельного JSON-файла рядом с DOCX:

```json
{
  "case_id": "work-001",
  "criteria": {
    "pr1.installation-report": {
      "score": 2,
      "manual_review_expected": false,
      "evidence_expected": true,
      "note": "Описаны исходное состояние и действия, этап не указан."
    }
  }
}
```

В `criteria` должны быть перечислены все критерии утверждённого набора для этой
работы. Иначе отсутствующие критерии будут считаться ошибкой автоматического
результата, а неожиданные дополнительные критерии — отдельным расхождением.
Перед запуском Ollama скрипт также проверяет, что каждый эталонный балл входит
в `allowed_scores`, а `null` сопровождается `manual_review_expected: true`.

`score` должен быть одним из `allowed_scores` утверждённого критерия. Для
неоднозначного случая указывается `manual_review_expected: true`; такой случай
не считается ошибкой, если система корректно сохранила `null` и объяснение.
`evidence_expected` по умолчанию равен `true`; для полностью пустого ответа,
где допустимо только техническое `DOC1:META:0001`, его можно явно поставить в
`false`. Технический metadata-ID не считается доказательством ответа.

## Как будем оценивать

Для каждого критерия сравниваются:

1. совпадение или допустимое расхождение балла;
2. корректность `manual_review`;
3. наличие реальных доказательств;
4. отсутствие ложного нуля при технической ошибке;
5. объяснимость расхождения по журналу аудита.

Итоговый JSON дополнительно содержит сводку по числу совпавших баллов,
`manual_review`, реальных доказательств и типам расхождений:
`score_mismatch`, `manual_review_mismatch`, `missing_real_evidence` и
`technical_failure_as_zero`.

Автоматический результат не будет считаться заменой решения преподавателя.
Набор закрывает этап качества только после разбора всех расхождений и явного
решения, какие расхождения допустимы, а какие требуют изменения критериев,
промпта или защитного правила.

## Порядок работы

1. Сначала запускается весь набор с одной зафиксированной версией модели и
   одинаковыми настройками Ollama.
2. Результаты и журналы сохраняются в отдельной локальной папке, не в Git.
3. Сводка группирует ошибки по типам: пропущенный балл, лишний балл,
   ложный `manual_review`, недостаточное доказательство и технический сбой.
4. Исправления вносятся только после разбора причины и сопровождаются новым
   регрессионным контролем.
5. После повторного запуска сравниваются не только итоговые баллы, но и
   решения по отдельным компонентам критерия.

Пока реальный набор не проверен, проект считается технически готовым к пилоту,
но не доказавшим качество автоматического оценивания.

## Локальный запуск

Структура набора:

```text
acceptance/
  work-001/
    student.docx
    expected.json
  work-002/
    student.docx
    expected.json
```

Запуск из корня репозитория:

```powershell
.venv\Scripts\python.exe scripts\evaluate_quality.py `
  --dataset C:\path\to\acceptance `
  --template C:\path\to\blank-template.docx `
  --criteria examples\pr1.criteria.approved.json `
  --approval examples\pr1.approval.json `
  --output C:\path\to\quality-report.json `
  --model qwen3.5:4b
```

Скрипт запускает тот же `student-ai-checker check --checked-scoring` для каждого
кейса, сохраняет отдельные результаты и журналы в соседней папке `*-runs`, а в
итоговом отчёте сравнивает балл, `manual_review` и наличие доказательств. Уже
существующие отчёт и папка запусков не перезаписываются.
