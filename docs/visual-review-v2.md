# Visual review v2 — данные, неопределённость и контроль

Статус: исправлен контракт наблюдений и правило блокировки. **Реальная Qwen с этой
правкой ещё не проверена; этап качества одной работы не закрыт.**
Режим остаётся `check --visual-review`. Этот документ уточняет `visual-review.md`.

## Диагноз по логу пользователя

Два реальных контроля вернули null вместо ожидаемых 1 и 0. В отрицательном примере
синтез описал имеющиеся изображения, но отказался от вывода именно из-за пометки
«недоверенные». Запрет исполнять инструкции оказался смешан с запретом анализировать
содержание. Предыдущая формулировка нашей процедуры допускала такую путаницу.

В положительном примере сработал application_safety_guard. В traceback нет исходного
балла и наблюдения, вызвавшего правило. Конкретный триггер этого запуска не установлен.
Независимо от этого в коде обнаружено широкое условие: любой непустой uncertainties
у relevant мог отменить балл. Теперь существенность сомнения задаётся явно.

## Что изменено

- Текст студента и наблюдения модели остаются данными без права давать команды.
  Их содержание разрешено использовать для предварительного анализа. Наблюдения
  остаются потенциально ошибочными, не новым evidence и не подтверждением учителя.
- В пользовательском сообщении используется `image_reviews`; в локальном аудите
  сохранены исходные ID, хеши и `model_output_is_untrusted=true`. Наблюдения никогда
  не подставляются в system message и не получают доступа к инструментам.
- Штатное отсутствие повторно приложенных пикселей на этапе синтеза явно отличено
  от отсутствующей картинки или технической ошибки.
- `uncertainties` v2 — объекты `detail` и `impact`: blocking для конкретного сомнения,
  способного изменить решение по текущему критерию; non_blocking для несущественного
  ограничения. [] допустим. Старый массив строк не принимается молча с новым смыслом.
- partly_readable/unreadable или relevance=uncertain требуют конкретного blocking.
  Для relevant нужно содержательное наблюдение. Эти связи проверяет Pydantic.
- readability относится к нужным визуальным признакам, не к наличию текста.
  `visible_text=[]` не означает техническую нечитабельность.
- relevance означает применимость проверки, НЕ выполнение требования. Наблюдаемое
  несоответствие тоже может относиться к критерию.
- Явно наблюдаемое отсутствие/несоответствие отличено от неизвестности. Нечитаемый
  потенциально подходящий источник по-прежнему не позволяет сделать отрицательный вывод.
- Guard записывает все причины в `guard_decisions`: ID, коды правил, relevance,
  readability, конкретные blocking-замечания. Сохраняется исходный ответ синтеза.
  Одни non_blocking-замечания сами по себе балл не отменяют.

Реальные материальные ограничения и положительный балл со ссылкой на not_relevant
по-прежнему блокируются. Валидный null остаётся null: нет автоматической подстановки
1/0, поиска большей оценки, повторов до успеха или исправления смысла регулярным
выражением. Классификация сомнений тоже выполняется моделью и может быть неверной.
Это остаётся ограничением качества, а не гарантией смысловой достоверности.

Критерии, утверждение, 25 баллов, модель, 16384 контекста, байты изображений и прежние
результаты не менялись. В production нет названий контрольных цветов, ожидаемых
ответов теста или ответа конкретного студента. `visual_review.pipeline_version=2`.

## Контрольные тесты

Сохранены прежние два синтетических изображения, их размеры, критерии, ожидания 1/0
и проверка ссылки на правильный источник. Набор из одних null всё ещё проваливается.
Изменены только читаемые имена случаев и сохранение журнала. Ожидания не передаются
в промпт. Один JSON теперь содержит оба случая, наблюдения, попытки и причины guard.

```powershell
git pull --ff-only
python -m pytest -m "not integration" -q
```

После успешных unit-тестов:

```powershell
$env:STUDENT_AI_CHECKER_NUM_CTX = "16384"
$env:STUDENT_AI_CHECKER_RUN_OLLAMA = "1"
$env:STUDENT_AI_CHECKER_TEST_ARTIFACT_DIR = "$HOME\Documents\StudentAIChecker\PR1\control-tests"
python -m pytest tests\integration\test_visual_review_real.py -v -s
```

В конце: `Контрольный журнал: ...\visual-controls-<время>-<id>.json`.
Журнал сохраняется также при провале assertions; старые файлы не перезаписываются.
Без переменной каталога используется временная папка pytest. Прерывание процесса
до teardown не гарантирует сохранения: это не checkpoint-система.

При провале не запускайте отчёт повторно: сначала нужен этот JSON. После прохождения
двух контролей повторите прежний `check --visual-review` с новым именем результата
и сравните объяснения с оригиналом. Один проход контроля не доказывает качество
на реальных документах. GUI и установщики Windows/macOS пока не начинаются.

## Реально выполненные проверки

Linux, Python 3.13.5, Pydantic 2.13.4, httpx 0.28.1, python-docx 1.2.0, pytest 9.0.2:

```text
tests/test_visual_review.py
tests/test_visual_review_contract.py
tests/integration/test_visual_review_real.py
90 passed, 2 skipped
```

90 тестов используют реальный код моделей, extractor, сравнения бланка, HTTP-клиента,
валидаторов, guard и CLI; сетевые ответы — явно обозначенные HTTP mocks только в
тестах. Два skipped — настоящие opt-in проверки: **Ollama здесь не запускался**.
Проверены также compileall, check --help, сохранность оригинальных пикселей контролей,
запись неуспешного аудита и отсутствие перезаписи. Это проверка программных инвариантов.
Зависимые Python-файлы рабочей копии сверены по blob SHA с базой
`e353346b1a8092ad9e50023395d0e75ea64f7747`.

Полный остальной набор проекта здесь не запускался. Локальный pytest 9 отличается
от проектного ограничения pytest>=8,<9; полный unit-набор нужно выполнить в окружении
пользователя. Студенческие DOCX, ответы, изображения и результаты не включены в коммит.

Справка API: https://docs.ollama.com/capabilities/structured-outputs — JSON Schema
передаётся через format, проверка Python-валидаторами остаётся отдельным шагом.
