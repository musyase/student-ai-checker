# Рабочий процесс преподавателя

Этот документ фиксирует основу будущего локального интерфейса поверх уже
существующего CLI и `result.json`. Интерфейс не должен заново оценивать работу:
его задача — показать проверяемые данные, объяснить сомнения и сохранить решение
преподавателя.

Уже доступен безопасный CLI-слой ручного решения:

```powershell
student-ai-checker review `
  --result result.json `
  --criteria examples\pr1.criteria.approved.json `
  --decisions teacher-decisions.json `
  --output reviewed-result.json
```

Формат решений:

```json
{
  "decisions": {
    "pr1.add-button": {
      "action": "set_score",
      "score": 2,
      "comment": "Проверено преподавателем."
    },
    "pr1.summary": {"action": "confirm"}
  }
}
```

Разрешены действия `confirm` и `set_score`. Балл при `set_score` проверяется по
`allowed_scores`. Отсутствующие решения оставляют reviewed-файл в состоянии
`pending`; частичная форма не может выглядеть как подтверждённая оценка.
Исходные `results`, доказательства и AI-аудит не изменяются. Новое поле
`teacher_review` содержит `source_result_sha256`, решения и `final_results`.

## Основной сценарий

```text
Выбрать работу и чистый шаблон
        ↓
Проверить критерии и approval
        ↓
Запустить локальную проверку
        ↓
Показать результаты и доказательства
        ↓
Преподаватель подтверждает или исправляет спорные пункты
        ↓
Сохранить проверку и экспортировать отчёт
```

## Состояния проверки

- `ready` — файлы и утверждённые критерии готовы;
- `processing` — локальная модель выполняет проверку;
- `completed` — все критерии получили допустимый предварительный результат;
- `manual_review` — хотя бы один критерий требует решения преподавателя;
- `failed` — техническая ошибка, результат нельзя считать оценкой.

Для слоя ручной проверки дополнительно используются состояния `pending` и
`completed`: второе появляется только после решения по каждому критерию.

Техническая ошибка никогда не показывается как нулевой балл. Для
`insufficient_evidence` и `unable_to_check` интерфейс обязан выделять ручную
проверку и показывать причину.

## Минимальный экран результата

На уровне работы:

- имя файла и SHA-256;
- версия критериев, шаблона и локальной модели;
- предварительная сумма без перевода в оценку 2–5;
- количество критериев, ожидающих ручного решения;
- кнопки «Открыть журнал» и «Экспортировать».

На уровне каждого критерия:

- название, максимум и предварительный балл;
- статус и объяснение;
- `manual_review_reason`, если он есть;
- список `evidence_ids` с реальным текстом или изображением;
- источник решения: текстовый, визуальный, детерминированный или защитное правило;
- действие преподавателя: подтвердить, изменить балл, добавить комментарий.

Показанный текст должен быть только тем, который пришёл из локального DOCX и
сохранён в `resolved_evidence`. Текст ответа модели отображается как
непроверенное объяснение, а не как доказанный факт.

## Минимальная модель хранения

Будущий SQLite-слой должен разделять:

- `submissions` — исходный DOCX, путь, SHA-256 и время загрузки;
- `rubric_approvals` — критерии, шаблон и approval-снимок;
- `grading_runs` — модель, настройки, версия конвейера и состояние запуска;
- `criterion_results` — предварительный результат по критерию;
- `evidence` — разрешённые фрагменты, привязанные к результату;
- `teacher_decisions` — подтверждение или исправление преподавателя;
- `audit_events` — технические ошибки, повторы и причины ручной проверки.

Сохранять нужно и первоначальный результат модели, и отдельное решение
преподавателя. Исправление преподавателя не должно переписывать исходный аудит.

## Границы MVP интерфейса

Первая версия интерфейса должна поддерживать одну работу за раз, локальный
запуск, просмотр доказательств и ручное подтверждение. Очередь группы,
автоматическое назначение итоговой оценки, облачная синхронизация и совместное
редактирование относятся к следующим этапам.
